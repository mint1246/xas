# Platform prerequisites and API choices

The first transport uses TCP with .NET `SslStream` and mutual certificate authentication. This works without native QUIC packages. [Microsoft's QUIC guidance](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/quic/quic-overview) says Linux needs a separate `libmsquic` installation and some networks block QUIC; QUIC can be evaluated later. TLS certificate handling follows [SslStream guidance](https://learn.microsoft.com/en-us/dotnet/core/extensions/sslstream-best-practices).

Windows virtual monitor support requires a separately built [IddCx UMDF indirect display driver](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/indirect-display-driver-model-overview). The [official sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-driver-samples/indirect-display-driver-sample/) is a starting point, not a signed deployable driver. Production distribution requires [Windows driver signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/develop/signing-a-driver) and appropriate packaging/testing.

Windows interactive terminal support requires [ConPTY](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole), available on Windows 10 version 1809 and later. The privileged helper must be an invisible service with secured local IPC and correct user-session token handling; [Windows services do not directly interact with the desktop](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services). It must never run remote requests as SYSTEM.

Windows filesystem mounts require the [WinFsp runtime/driver](https://winfsp.dev/rel/). Verify the chosen [upstream API and licensing](https://winfsp.dev/apiref/) before packaging. Linux mounts require FUSE/libfuse and access to `/dev/fuse`; upstream documents [mount permissions and options](https://github.com/libfuse/libfuse/blob/master/doc/mount.fuse3.8).

Wayland global input must go through an approved [RemoteDesktop portal session](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html), preferably `ConnectToEIS`/libei where supported. Availability and consent depend on the installed portal backend and desktop session. [libei](https://libinput.pages.freedesktop.org/libei/) has a native C API, likely requiring a small helper. Linux interactive shells need an actual PTY, for example [forkpty/openpty](https://www.man7.org/linux/man-pages/man3/openpty.3.html).

The included Linux PTY helper builds with `make` in `native/linux-pty` on a Linux host with a C compiler and `libutil`. Put `xas-linux-pty` on `PATH` or set `XAS_LINUX_PTY_HELPER` to its absolute path. Linux compilation and runtime validation remain outstanding on this Windows development host.
